# REST API, event stream and MCP

The daemon's web server (default port 4711) serves three things for programs, each with its
own switch in Options → Web Interface:

| Surface | Path | Switch (`preferences.yml`, `webserver:`) | Default |
|---|---|---|---|
| REST API | `/api/v1/*` | `restApiEnabled` | off |
| MCP endpoint for AI assistants | `/mcp` | `mcpEnabled` (+ `mcpReadOnly`) | off |
| Template web UI | `/` | `enabled` | off |

They share the port, the listen address, HTTPS and the API key (`apiKey`). Listening on all
interfaces, the server does not start when another program already uses the port on one local
address (`127.0.0.1`, for instance): requests to that address would reach that program. The log
names the address. When a surface is on, the daemon logs its address at start:

```
WebServer: REST API playground at http://localhost:4711/api/v1/docs
WebServer: OpenAPI document at http://localhost:4711/api/v1/openapi.json
WebServer: MCP endpoint at http://localhost:4711/mcp
```

## Where the API is described

- **`GET /api/v1/openapi.json`** — the OpenAPI 3.1 document, generated by the running daemon.
  A copy is checked in as `docs/openapi.json`; a test fails when it is stale
  (`EMULE_WRITE_OPENAPI=1 ./tst_WebServer api_checkedInOpenApiIsCurrent` rewrites it).
- **`GET /api/v1/docs`** — Swagger UI on that document. Press *Authorize*, paste the API key,
  and every route can be tried from the page. The page and its two files are served by the
  daemon itself (`webserver/swagger-ui-bundle.js`, `swagger-ui.css` in the program folder's
  bundled `config/`; a copy in the config directory's `webserver/` overrides it); nothing is
  loaded from the internet.

Neither needs a key: a browser cannot send a header for a page load, and they hold no secrets.
Every call does.

## Conventions

- **Key:** `X-Api-Key: <key>` or `Authorization: Bearer <key>`. `/health` needs none.
- **Errors:** `{"error": {"code": <HTTP status>, "message": "..."}}`, also for an unknown route.
- **Strict input:** an unknown query parameter or body field is a `400`, as is a value of the
  wrong type or out of range. Nothing is ignored silently.
- **Lists:** `{items, total, offset, limit}`; `?limit=` 1–1000 (default 100), `?offset=`.
- **Destructive calls** (cancel an eD2K or ed3k download, remove a Usenet release, a hoster
  download or a category, shut down, restart)
  need `"confirm": true` in the body, or `?confirm=true` on `DELETE`.
- **Version:** every response carries `X-Contract-Version`; `GET /capabilities` lists the
  features and every operation id.

## Events

`GET /api/v1/events` is a `text/event-stream`. Most events say only that a list changed —
fetch it again:

| Event | Data |
|---|---|
| `downloads.changed`, `uploads.changed`, `shared.changed`, `friends.changed`, `categories.changed`, `usenet.changed`, `search.results` | none |
| `downloads.completed` | `hash`, `fileName` |
| `connection.changed` | `connected`, `connecting`, `lowID`, `firewalled`, `netBlocked`, server |
| `kad.changed` | `running`, `connected`, `firewalled` |
| `nat.changed` | `statusText`, `methodText`, `externalAddress` |
| `search.state` | `searchID`, `state`, `hasMore` |
| `usenet.finished` | `id`, `success`, `message` |
| `sync.reset` | the gap could not be replayed: fetch everything again |

`?topics=downloads,search` limits the stream to those prefixes. `Last-Event-ID` (or
`?lastEventId=`) resumes from the daemon's ring of the last 1,000 events. A comment line
arrives every 15 seconds. A "changed" event is sent at once and then at most once a second
per type. Statistics, log lines and chat are not pushed; poll `/stats` and `/logs?since=`.

## Media player links

The stream routes answer HTTP ranges, so a media player can seek in them. They take a stream
token in `?token=`, not the API key, because a player cannot send a header. A REST client gets
the link with its key:

| Link call (API key) | Stream it returns (`?token=`) |
|---|---|
| `GET /downloads/{hash}/preview-link` | `/downloads/{hash}/preview` — eD2K hash (32 hex) or ed3k root (64), download or shared file |
| `GET /usenet/{id}/{fileIndex}/preview-link` | `/usenet/{id}/{fileIndex}/preview` |
| `GET /torrents/{id}/{fileIndex}/preview-link` | `/torrents/{id}/{fileIndex}/preview` — `fileIndex` -1 = largest file |
| `GET /hoster/{id}/preview-link` | `/hoster/{id}/preview` — video/audio items only; archive or other file: 406 |

The answer is `{url, path, token}`: `url` is absolute, built from the request's scheme and
`Host`, and goes straight to the player. Each call mints a new token; it lapses after 6 hours
unused, and only the 16 newest stay valid. The MCP tools (`download_preview_link`,
`usenet_preview_link`, `torrents_preview_link`, `hoster_preview_link`) give `path` only.

Unfinished files: with *Enable seeking in downloads* (`downloadSeeking`, off by default) a
range that is not on disk yet waits while the core fetches those bytes first: 60 seconds for
eD2K/ed3k parts, web-seed ranges and torrent piece deadlines. Usenet and hoster previews always
do this, with the switch on or off (both are fast, a preview is a request for those bytes): 60
seconds for hoster items, 15 seconds for Usenet articles (the item is boosted too). A hoster's own HTTP stream stays in file order; only
ed3k peers of an item with a known root fetch the seek point first, so a seek ahead of a
rootless hoster item waits for the stream to get there. Near the end (the last 64 MiB, where an
MP4 keeps its index `moov` when it is not "faststart") a direct web link or a premium login
(own or multi-hoster, two connections or more) opens the link a second time from the seek
point, so the player starts at once; the stream fetches those bytes again later, and only its
bytes are hashed. Only a preview read starts it. A free hoster would ask another puzzle or wait, so such an MP4 opens only
once the item is nearly complete. A stream the resolver muxes
(HLS, DASH through ffmpeg) has no bytes before it ends: 406 until complete, unless ed3k peers
deliver blocks. Off, eD2K/ed3k and torrent files are served as they are on disk, gaps
included.

The web UI links the same routes with a page token (30 minutes idle, kept alive by the
session): *Preview* in the Transfers and Shared Files right-click menus, in the Usenet menu,
and on each row of a torrent's file table.

## Networks

| Prefix | What | Needs |
|---|---|---|
| `/downloads`, `/shared`, `/servers`, `/kad`, `/search` | eD2K and Kad | — |
| `/ed3k/downloads` | ed3k downloads, by 64-hex root: list, add `ed3k:` links, pause/resume, rename, priority, category, move, cancel | ed3k on |
| `/usenet` | Usenet queue | Usenet on |
| `/torrents` | BitTorrent | a BitTorrent build, BitTorrent on |
| `/hoster` | hoster/web-link downloads: list, add links (optional package), DLC/RSDF/CCF container (base64), pause/resume/retry, remove | ed3k on + hoster resolver |
| `/indexers`, `/indexer/searches` | newznab (Usenet) and torznab (torrent) indexer searches: list accounts, search, results, download, stop, remove | an indexer in Options |

A network that is off answers `503`. `PATCH /shared/{hash}` renames a shared file, sets its
upload priority or your comment and rating; `POST /downloads/{hash}/move` moves an unfinished
download to another temp folder.

`POST /search` takes `"type": "ed3k"` too. `POST /search/{id}/download` takes any row of its
search: an eD2K file is queued; an ed3k file (`metaKind` `"ed3k"`, `ed3kRoot`) goes to the ed3k
downloads; a Usenet, torrent or web release of a `usenetServer` / `torrentServer` / `webServer`
search is fetched from the server's catalogue and handed to the Usenet queue, Torrents or Hoster —
that call answers once it is there.
A torrent row of such a search also carries `metaSeeders` and `metaPeers`: the catalogue's last
seeder and leecher counts (`metaPeers` excludes seeders). A field is left out when the catalogue
sent no count — it sends none for 0, so absent means unknown or 0. `sourceCount` is unchanged.

Indexer searches have their own ids (the GUI's own searches are listed too).
`POST /indexer/searches` takes `query`, `network` (`usenet` or `torrent`), `mode`
(`search`, `tvsearch`, `movie`) with `season`/`episode`/`imdb`, newznab `categories`, size
bounds and `indexers` (names from `GET /indexers`); `409` when no indexer serves the network.
Every enabled account is asked at once, so poll `GET /indexer/searches/{id}/results` until the
search's `running` is false. `POST /indexer/searches/{id}/download` with the row's `id` as
`result` fetches its .nzb, .torrent or magnet (one of the indexer's daily grabs) and adds it to
the Usenet queue or Torrents; `409` with an `outcome` is "already downloaded", which `force`
answers; `502` is a failed fetch. API keys and download URLs never leave the daemon.

## Preferences

`GET /api/v1/preferences/schema` lists every preference the API offers with type, range, unit,
default, `restartRequired` and `writable`. `PATCH /api/v1/preferences` checks the whole body
against it before changing anything, then stores through the same code a GUI save runs.
Credentials, API keys and anything naming a program or certificate are not in the schema and
cannot be read or set here; the web server's own switches are shown but read-only.

`port` and `udpPort` can be set. The reply then says in `listenPorts` what happened:

```json
"listenPorts": { "result": "applied", "tcpPort": 12346, "udpPort": 12345 }
```

| `result` | Meaning |
|---|---|
| `unchanged` | no port moved |
| `applied` | listening on the new ports now |
| `restartRequired` | connected to a network or peer, or UDP switched on/off: saved, the old ports stay until the daemon restarts |
| `bindFailed` | a new port is in use by another program: that socket stays on its old port |

`tcpPort`/`udpPort` are the ports listening at that moment, `0` for a closed socket. Sending
`bindAddress` in the same patch reopens every socket on the new interface and the new ports at
once, connected or not; UDP switched on/off then applies too, unless the daemon started with it off.
The web server's own port is not touched. `POST /api/v1/app/restart` (body `{"confirm":true}`)
applies a `restartRequired` change: the daemon saves state, exits and starts again with the same
arguments, the same as the GUI's Restart Now. On Linux and macOS it stays the same process (same
PID, fine as a container's PID 1); attached GUIs wait for it and reconnect. The API is gone for a
few seconds; poll `GET /api/v1/app` until it answers. `POST /api/v1/app/shutdown` only stops it.

`bindAddress` needs no restart. The reply says in `network` what the change did:

| `network.result` | Meaning |
|---|---|
| `unchanged` | no change, or it resolves to the interface the sockets are already on |
| `reopened` | every connection was closed and the sockets reopened on the new interface; eD2K and Kad reconnect (new client ID, Kad firewall re-checked), port mapping restarts |
| `waiting` | the interface is not present: nothing connects until it appears, then it reconnects by itself |

Every other writable key takes effect at once except the ones the schema marks
`restartRequired`: `port`/`udpPort` while connected (see above) and `useSecureIdent`. A few apply
to what comes next by design and say so: `networkED2K`, `kadEnabled`, `autoConnect` and
`autoUpdateServerList` act at start; `autoDownloadPriority`/`autoSharedFilesPriority` act on
new files; obfuscation switches act on new connections.

## MCP

`POST /mcp` speaks the Model Context Protocol over streamable HTTP, stateless, tools only, in
protocol revision **2026-07-28** and no other. There is no `initialize` handshake: every request
names the revision in `params._meta["io.modelcontextprotocol/protocolVersion"]` and mirrors it,
the method and the tool name into the `MCP-Protocol-Version` / `Mcp-Method` / `Mcp-Name`
headers. `server/discover` describes the server. One message per POST; `GET` and `DELETE`
answer 405.

A client of an older revision (one that opens with `initialize`, or names no revision) gets
HTTP 400 with the JSON-RPC error `-32022` listing the supported revision, so it can say what is
wrong instead of failing silently. Headers that are missing or disagree with the body are
`-32020` (400); an unknown method is `-32601` (404).

The tools are operations of the same table as the REST routes — same validation, same code —
chosen for what an assistant needs (status, search, downloads, servers, Kad, shared files,
categories, preferences, logs, Usenet, torrents, ed3k downloads, hoster downloads, indexer searches). The OpenAPI document marks them with `x-mcp-tool`.
Shutting the daemon down is not a tool. With `mcpReadOnly` only the tools that change nothing
are offered. A request with an `Origin` header that is neither this server nor on
`corsAllowedOrigins` is refused.

**A client that speaks HTTP** (Claude Code, for example):

```
claude mcp add --transport http emuleqt http://localhost:4711/mcp --header "Authorization: Bearer <api key>"
```

**A client that only starts a local program** uses the bridge `emuleqt-mcp`, which reads the
port and key from the local configuration and adds the headers the HTTP transport needs. It
ships next to the daemon: in the folder of the Linux tarball and the Windows zip, and in
`Contents/MacOS/` of the app bundle on macOS. The client itself has to speak 2026-07-28.

```json
{ "mcpServers": { "emuleqt": { "command": "/path/to/emuleqt-mcp" } } }
```

For a daemon on another machine: `emuleqt-mcp --url http://host:4711/mcp --api-key <key>`
(or `EMULEQT_API_KEY`; `--insecure` accepts a self-signed certificate, `--config <dir>` picks
another configuration directory).

## For contributors

A route exists only as an entry of the table in `src/core/webserver/WebServerApi.cpp`
(`api::Operation`: path, parameters with type and range, flags, handler). Routing, validation,
the OpenAPI document and the MCP tool list are generated from it. Actions go through
`src/core/app/CoreOps.h`, which the IPC handlers call too; what only the daemon can do sits
behind `ApiBackend`.
